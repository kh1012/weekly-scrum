# /my 페이지 성능 분석 보고서

## 요약

`/my` 페이지의 초기 로딩 성능 분석 결과, 서버 사이드에서 다수의 데이터베이스 쿼리와 집계 연산이 수행되어 페이지 렌더링이 완료되기까지 상당한 시간이 소요될 수 있습니다.

## 1. 페이지 구조

### Layout (`src/app/(scrum)/layout.tsx`)

Layout은 모든 `/scrum` 하위 페이지에서 공통으로 실행됩니다.

실행되는 데이터 로딩

1. 프로필 확인 (2회 쿼리)

   - `profiles` 테이블 조회

2. Workspace Role 조회

   - `workspace_members` 테이블 조회

3. 메뉴 설정 조회 (`getMenuSettings`)

   - `menu_settings` 테이블 조회

4. 메뉴 조회수 데이터 (`getMenuViewCounts`)

   - `user_menu_visits` 테이블 조회 (최근 8주)

5. 메뉴 통계 (`getMenuStats`)

   - `feedbacks` 테이블 집계
   - `snapshots` 테이블 집계
   - `snapshot_entries` 테이블 집계
   - `plans` 테이블 집계

6. 메뉴 새 데이터 개수 (`getMenuNewCounts`)

   - 여러 테이블에서 최근 데이터 개수 조회

7. 스냅샷 데이터 (`getSupabaseOnlyData`)
   - `snapshots` 테이블 전체 조회
   - `snapshot_entries` 테이블 전체 조회 (JOIN)

**총 쿼리 수: 약 10-15개**

### Page (`src/app/(scrum)/my/page.tsx`)

Page는 `/my` 페이지에서만 실행됩니다.

실행되는 데이터 로딩

1. 프로필 조회 (또 다시)

   - `profiles` 테이블 조회

2. 개인 대시보드 메트릭 (`getPersonalDashboardMetrics`)

   - Snapshot 메트릭

     - `snapshots` 테이블 조회 (모든 스냅샷)
     - `snapshot_entries` 테이블 조회 (모든 엔트리)
     - 주차별 그룹핑 및 카운팅 (메모리 연산)

   - Plan 메트릭

     - `plan_assignees` 테이블 조회
     - `plans` 테이블 조회 (할당된 Plans)

   - Usage 메트릭

     - `menu_events` 테이블 조회 (최근 14일)
     - 집계 연산 (메모리)

   - 추가 데이터
     - 최근 엔트리 5개 조회
     - 도메인/프로젝트 분포 집계 (메모리)
     - 주차별 엔트리 수 추이 (최근 8주, 메모리 연산)
     - 주차별 평균 진행률 추이 (최근 8주, 메모리 연산)

**총 쿼리 수: 약 8-12개**
**메모리 집계 연산: 다수**

## 2. 성능 병목 원인 분석

### 2.1 데이터 로딩 (쿼리)

Layout + Page에서 총 **20-30개의 데이터베이스 쿼리**가 순차적으로 실행됩니다.

주요 문제점

- 쿼리가 직렬로 실행됨 (병렬 처리 부족)
- 중복 쿼리 (프로필 조회 2-3회)
- 전체 데이터 조회 후 메모리에서 필터링/집계
- N+1 쿼리 패턴 (스냅샷 -> 엔트리)

### 2.2 연산 (집계)

서버 사이드에서 수행되는 주요 연산

1. 주차별 스냅샷 그룹핑
2. 도메인/프로젝트 분포 계산
3. 주차별 엔트리 수 추이 계산
4. 주차별 평균 진행률 계산 (past_week 필드의 tasks 배열 순회)
5. 메뉴 조회수 집계
6. Top Routes 계산

연산 복잡도

- 스냅샷 데이터가 많을수록 연산 시간 증가
- 최악의 경우 O(n²) 복잡도 (스냅샷 x 엔트리)

## 3. 추정 로딩 시간

### 시나리오 1: 적은 데이터 (< 10 스냅샷, < 100 엔트리)

- 쿼리 시간: 200-500ms
- 집계 연산: 50-100ms
- 네트워크 오버헤드: 50-100ms
- **총 예상 시간: 300-700ms**

### 시나리오 2: 중간 데이터 (10-50 스냅샷, 100-500 엔트리)

- 쿼리 시간: 500-1500ms
- 집계 연산: 100-300ms
- 네트워크 오버헤드: 50-100ms
- **총 예상 시간: 650-1900ms (0.7-2초)**

### 시나리오 3: 많은 데이터 (> 50 스냅샷, > 500 엔트리)

- 쿼리 시간: 1500-3000ms
- 집계 연산: 300-1000ms
- 네트워크 오버헤드: 50-100ms
- **총 예상 시간: 1850-4100ms (2-4초)**

## 4. SNB 페이지 전환이 빠른 이유

SNB (Side Navigation Bar)를 통한 페이지 전환이 빠른 이유는 Next.js의 prefetch 기능 때문입니다.

Prefetch 동작 방식

1. 링크가 뷰포트에 보이면 자동으로 prefetch 시작
2. 백그라운드에서 페이지 데이터를 미리 로딩
3. 사용자가 클릭할 때는 이미 로딩된 데이터를 사용
4. 실제 느껴지는 로딩 시간이 거의 없음

강제 새로고침 시 차이점

- Prefetch 캐시가 비워짐
- 모든 데이터를 처음부터 다시 로딩
- Layout + Page의 모든 쿼리가 실행됨
- **실제 로딩 시간이 그대로 드러남**

## 5. 개선 제안

### 5.1 즉시 적용 가능한 개선

1. 중복 쿼리 제거

   - 프로필 조회를 한 번만 수행하고 재사용

2. 쿼리 병렬화

   - 독립적인 쿼리들을 `Promise.all`로 병렬 실행
   - 예상 개선: 30-50% 시간 단축

3. 필요한 데이터만 조회
   - `select *` 대신 필요한 필드만 선택
   - 엔트리 전체 조회 대신 집계 쿼리 사용

### 5.2 중기 개선 (아키텍처 변경)

1. 데이터베이스 뷰 또는 Materialized View 사용

   - 집계 데이터를 미리 계산하여 저장
   - 페이지 로딩 시 집계된 데이터만 조회

2. 캐싱 레이어 추가

   - Redis 등을 사용하여 자주 조회되는 데이터 캐싱
   - TTL 설정으로 데이터 신선도 유지

3. 증분 로딩 (Progressive Loading)
   - 핵심 데이터만 먼저 로딩하여 빠르게 렌더링
   - 차트 등 부가 데이터는 클라이언트에서 추가 로딩

### 5.3 장기 개선 (근본적인 변경)

1. 클라이언트 사이드 렌더링으로 전환

   - 서버는 API만 제공
   - 클라이언트에서 React Query 등을 사용하여 데이터 관리
   - 로딩 상태를 사용자에게 명확히 표시

2. 백그라운드 집계 작업

   - Cron Job으로 정기적으로 집계 데이터 계산
   - 페이지 로딩 시에는 계산된 결과만 조회

3. 데이터 파티셔닝
   - 오래된 데이터는 별도 테이블로 분리
   - 최근 데이터만 빠르게 조회

## 6. 성능 측정 방법

브라우저에서 직접 측정할 수 있는 도구를 제공합니다.

사용 방법

1. 개발 서버 실행 (`yarn dev`)
2. 브라우저에서 `http://localhost:3000/measure-performance.html` 접속
3. 측정할 페이지 경로 입력 (기본값: `/my`)
4. 반복 횟수 입력 (기본값: 100)
5. "테스트 시작" 버튼 클릭
6. 결과 확인 및 JSON으로 저장 가능

측정 항목

- 전체 로딩 시간 (페이지 접속 ~ Network Idle)
- TTFB (Time To First Byte) - 서버 응답 시간
- DOM 파싱 시간
- 완전 로딩 시간
- 시간대별 분포

## 7. 적용된 개선 사항

2026-01-10 기준으로 다음의 성능 개선이 적용되었습니다.

### 7.1 적용된 최적화

1. N+1 쿼리 패턴 제거

   - snapshot_entries를 4번 조회하던 것을 1번의 병렬 쿼리로 통합
   - plan_assignees 조회 후 plans를 순차 조회하던 것을 JOIN으로 한 번에 조회

2. 데이터 재사용

   - snapshot_entries를 한 번 조회하여 모든 집계에 재사용
   - 메모리 집계로 추가 데이터베이스 호출 제거

3. 필요한 필드만 선택
   - 모든 필요한 필드를 초기 쿼리에서 한 번에 조회
   - 네트워크 전송량 감소

### 7.2 성능 개선 결과

- 쿼리 수: 8-12개 → 4개로 감소 (50-66% 감소)
- 예상 로딩 시간 개선: 30-50%
  - 중간 데이터 기준: 0.7-2초 → 0.4-1초

### 7.3 개선된 쿼리 구조

```typescript
// 모든 독립적인 쿼리를 한 번에 병렬 실행
Promise.allSettled([
  snapshots 조회,
  snapshot_entries 조회 (모든 필드),
  plan_assignees + plans 조회 (JOIN),
  menu_events 조회,
]);
```

## 8. 결론

`/my` 페이지의 초기 로딩이 느린 주요 원인은

1. 다수의 데이터베이스 쿼리 (20-30개)
2. 서버 사이드 집계 연산
3. 쿼리의 순차적 실행

이었으며, 현재는 쿼리 병렬화 및 N+1 패턴 제거를 통해 상당 부분 개선되었습니다.

SNB를 통한 페이지 전환이 빠른 것은 Next.js의 prefetch 덕분이며, 강제 새로고침 시에는 모든 쿼리와 연산이 다시 실행되어 실제 로딩 시간이 드러납니다.

추가 개선을 위해서는

- 데이터베이스 인덱스 최적화
- 캐싱 레이어 추가
- 증분 로딩
- 백그라운드 집계

등의 아키텍처 변경이 필요합니다.
